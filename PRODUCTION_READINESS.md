## Confirmed security findings

- **P1 / locked-firm page reads were relying on the app shell's lock screen.** Tenant pages queried client, matter, member, firm settings, practice profile, legal update, and library data after resolving only the active tenant; the shell's conditional lock screen was not a sufficient data authorization boundary. The installed Next.js 16 auth guide explicitly states that a layout that hides/swaps children does not stop route segments from rendering or appearing in the RSC payload. All tenant pages now gate before their data queries with `getCurrentTenantIfEntitled`; the billing route remains accessible and mutating actions already use `getCurrentEntitledTenant`. The helper has local locked/entitled-state tests. Browser-level RSC response inspection remains outstanding.
- **P0 / connector token audience is not verified.** The protected-resource metadata names the MCP resource URL, but Clerk's OAuth token verification does not currently prove that the token is issued for this MCP resource. The app now additionally checks Clerk's verified token record against the authenticated user and OAuth client and requires the record to contain the OAuth type and connector scopes. This prevents identity/record mismatch, but does not bind the token's audience to the MCP URL. Clerk's docs describe OAuth token verification and client/scopes in introspection; they do not establish a resource-specific `aud` for this server. Do not expose sensitive firm tools publicly until access-token audience behavior is verified and resource-bound authorization is enforced, or the connector uses an authorization server that supports it. References: [Clerk OAuth token verification](https://clerk.com/docs/guides/configure/auth-strategies/oauth/verify-oauth-tokens), [Clerk OAuth implementation and token formats](https://clerk.com/docs/guides/configure/auth-strategies/oauth/how-clerk-implements-oauth), [Clerk token introspection](https://clerk.com/docs/guides/configure/auth-strategies/oauth/single-sign-on), [OpenAI connector auth requirements](https://developers.openai.com/plugins/build/auth).
- **P1 / Clerk-side revocation and membership behavior remain externally unverified; local stale-state gaps closed.** The prior fail-open behavior is fixed: if Clerk's token-status service errors, the connector returns a retryable server error. Connector authentication rejects JWT access tokens because the installed Clerk SDK verifies those locally and cannot establish current revocation status. It requires opaque OAuth access tokens, resolves the user and selected `org_id` from HTTPS Clerk `/oauth/userinfo`, and checks token status with Clerk on every request without a local revocation cache. Banned/locked state and membership in the selected organization are also fetched from Clerk on every request, without caching; the organization lookup is constrained to that selected organization. Configure the production Clerk OAuth application to issue opaque access tokens and verify live token revocation, ban/lock, and organization-removal behavior before launch. References: [Clerk token formats](https://clerk.com/docs/guides/development/machine-auth/token-formats), [Clerk OAuth token verification](https://clerk.com/docs/guides/configure/auth-strategies/oauth/verify-oauth-tokens).
- **Service-context GUC is a broad database bypass, not authorization.** The PGlite test confirms `app.is_service_role = 'true'` allows cross-tenant RLS visibility when set by the app-like database role. Keep this setting behind authenticated, server-owned service call paths; never rely on the GUC itself to authorize a user-facing operation. Review every `withServiceContext` caller and verify database role configuration in Neon.
